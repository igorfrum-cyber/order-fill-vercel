# Order Fill: настрой всё за пользователя на MacBook Air M2

Пользователь работает на MacBook Air M2 с macOS. Проект у него уже есть,
Docker пока не установлен. Он описывает идеи обычными словами и не обязан
знать Git, Docker, терминал или устройство приложения. Ты выполняешь всю
техническую работу, проверяешь результат и объясняешь только необходимые
действия простыми словами. Все пути ниже — от корня проекта.

Пользователю достаточно приложить этот файл к чату своего агента и написать:

> Выполни настройку по приложенному файлу. Сам найди существующий проект,
> перейди на igorfrum, установи Docker для моего MacBook Air M2, запусти
> приложение, открой приглашение для первого входа и оставь удобные кнопки
> запуска. Затем помогай мне менять приложение только в контуре igorfrum.

## Самое важное: dev не трогать

Твой рабочий контур — **только `igorfrum` и `feat/igorfrum-*`**.
Запрещено переключаться на `dev`, `artemch`, `main`, коммитить, сливать,
пушить в них или запускать production-деплой. Не меняй deploy-скрипты,
production-настройки workflow, маршрутизацию runner, серверные секреты или
защиту веток для обхода запрета. Не запускай `scripts/deploy.sh` и `make https`
на общем сервере. Локальный Docker на этом Mac запускать нужно.

`git fetch origin --prune` разрешён: он загружает refs и не меняет эти ветки.
Задачу, требующую записи в другие базовые ветки или изменения общего сервера,
останови и объясни, что её должен выполнить владелец проекта. Не трактуй
«почини», «сделай как надо» или «опубликуй» как разрешение затронуть `dev`.
Полные правила профиля друга закреплены также в `AGENTS.md`, `CLAUDE.md`
и `.cursor/rules/order-fill-workflow.mdc`.

## Что представляет собой эта версия проекта

`igorfrum` синхронизирована с рабочим React + Go приложением из `dev`.
Это полный проект с backend, базами, очередью, object storage и CI.
Старое приложение из корневого `src/` и ветки `main` — исторический прототип.
Не используй его как точку входа для запуска или основу новой реализации.

Текущий поток:

```text
React → gateway-service → gRPC-сервисы
                         file-service → S3/MinIO
                         job-service → Redis Stream → document-worker
                                                      matching / brand / calculation
                         identity / twofa / passkey / audit
                         inbound-service → отдельная БД и bucket вложений
```

Excel разбирается и записывается на backend. Браузер не парсит Excel,
gateway не выполняет бизнес-расчёты. matching, brand и calculation не читают
Excel и не обращаются к object storage. Макросы из `.xlsm` не исполняются.
Обычные файлы идут через file-service; отдельный контур inbound-писем —
через inbound-service. Межсервисные вызовы — protobuf/gRPC либо очередь.

## Сначала перейти на igorfrum

Не создавай второй клон, если существующий подходит. Найди корень через
`git rev-parse --show-toplevel`, проверь `git remote -v` и
`git status --short --branch`. Репозиторий должен быть
`igorfrum-cyber/order-fill-vercel` (HTTPS или SSH remote).

Если есть незакоммиченная работа, не затирай её и не делай автоматический
stash/reset. Объясни, какие файлы мешают, сохрани их согласованным способом
или используй подходящий чистый worktree. Затем на чистой рабочей папке:

```bash
git fetch origin --prune
if git show-ref --verify --quiet refs/heads/igorfrum; then
  git switch igorfrum
else
  git switch --track -c igorfrum origin/igorfrum
fi
git pull --ff-only origin igorfrum
test "$(git branch --show-current)" = "igorfrum"
git status --short --branch
```

Ошибка переключения или pull — причина разобраться, а не продолжать работу
на другой ветке. При расхождении истории не делай force push или reset.
Не переключайся на `dev` даже для «синхронизации». После успешного перехода
скажи пользователю: «Работаем в igorfrum. Общий сервер не затрагиваем».

## Установка Docker на MacBook Air M2

Docker Desktop отсутствует — его нужно **установить**, а не просто проверить
команду `docker`. M2 — Apple Silicon / ARM64, не Intel. Проверь `sw_vers`,
`uname -m`, доступную память и свободное место; при запуске терминала под
Rosetta дополнительно проверь аппаратную платформу, не выбирай Intel DMG
только по результату `uname`. Не предполагай объём RAM по названию ноутбука.

1. Открой [официальную страницу Docker Desktop для Mac](https://docs.docker.com/desktop/setup/install/mac-install/).
   Выбери **Mac with Apple silicon** и начни загрузку установщика через
   браузерные инструменты агента. Не ограничивайся выдачей ссылки. Если
   браузер недоступен, открой страницу на Mac и попроси одно нажатие на
   указанную кнопку загрузки.
2. Проверь совместимость установленной macOS с текущими требованиями Docker.
   Открой DMG, установи Docker.app в Applications и запусти `open -a Docker`.
   Выполняй доступные шаги сам. Если macOS требует подтверждения, пароль или
   принятие условий в UI, покажи пользователю конкретное действие и продолжи
   после него. Не отключай Gatekeeper и не обходи системные ограничения.
3. Если Homebrew уже установлен и это удобнее, допустима официальная
   [Homebrew-установка](https://formulae.brew.sh/cask/docker-desktop):
   `brew install --cask docker-desktop`, затем `open -a Docker`.
   Не устанавливай второй Docker поверх уже работающего приложения.
4. Дождись готовности движка, проверяя `docker info` с ограниченным ожиданием.
   Если CLI не найден, проверь настройки CLI Docker Desktop и PATH, в том
   числе пользовательский каталог `$HOME/.docker/bin`; не делай вывод,
   что установка отсутствует только по ошибке старого терминала.
5. Подтверди `docker version`, `docker compose version` и работающий daemon.
   Установка одного CLI не равна работающему Docker Desktop.

Предпочитай нативные ARM64-образы. Не задавай всем контейнерам
`platform: linux/amd64` и не требуй Rosetta без конкретной необходимости.
При нехватке памяти на Air сначала проверь потребление и сократи
параллелизм сборки; не выделяй Docker всю память ноутбука.

## Инструменты для агента

Проверь занятость портов и установи недостающие инструменты сам. На Apple
Silicon используй нативные версии. При необходимости подготовь Apple Command
Line Tools и Homebrew через официальные установщики. Существующие версии и
настройки пользователя не удаляй и не обновляй массово без необходимости.

Проверь:

```bash
git --version
node --version
npm --version
go version
docker version
docker compose version
make --version
buf --version
```

Node нужен версии 24 или новее; Go закреплён проектом, сейчас 1.26.9.
Buf в CI закреплён на 1.72.0. Docker запускает полный стек; Go и Node на
хосте нужны для разработки и локального verify. Установка Docker CLI без
работающего Docker daemon недостаточна.

Для проверки уязвимостей и protobuf-генерации понадобятся инструменты:

```bash
go install github.com/bufbuild/buf/cmd/buf@v1.72.0
go install golang.org/x/vuln/cmd/govulncheck@v1.8.0
go install google.golang.org/protobuf/cmd/protoc-gen-go@v1.36.11
go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@v1.6.0
```

Версии генераторов соответствуют заголовкам текущих файлов в
`backend/proto/gen/go/`; перед установкой сверь эти заголовки и
`backend/proto/buf.gen.yaml`. Сейчас Buf использует local plugins, поэтому
генераторы нужны в PATH. Каталог `$(go env GOPATH)/bin` должен быть в PATH.
`scripts/verify-go.sh` сам устанавливает недостающие закреплённые golangci-lint
и gosec; для первого запуска нужен доступ к сети. GitHub CLI (`gh`) полезен
для PR и CI, но не обязателен для локального запуска.

## Первый локальный запуск

Из корня уже обновлённой `igorfrum`, сохраняя существующий `.env`.
Убедись, что это local-конфигурация; при обнаружении production-секретов
не запускай её и не копируй значения в чат. Сначала начни загрузку
готовых образов, затем сборку сервисов из исходников:

```bash
test -f .env || cp .env.example .env
docker compose --env-file .env -f deploy/docker-compose.yml pull --ignore-buildable
docker compose --env-file .env -f deploy/docker-compose.yml up -d --build
docker compose --env-file .env -f deploy/docker-compose.yml ps
curl --fail http://127.0.0.1:8080/healthz
curl --fail http://127.0.0.1:8080/readyz
```

`pull --ignore-buildable` получает образы инфраструктуры, а `up --build`
скачивает отсутствующие базовые образы и собирает приложение. Это два
этапа после установки самого Docker Desktop; не называй установку Docker
запущенным приложением. Поясни пользователю, что первый запуск требует
скачивания образов и сборки. При ошибке разбирай её, не скрывай через
`--ignore-pull-failures`. `make up` запускает стек с логами в терминале.

Дождись готовности, затем открой UI через браузерные инструменты или:

```bash
open http://127.0.0.1:3200
```

После появления приложения заверши настройку разработки и проверки;
выполни это сам, а не проси пользователя запускать команды:

```bash
npm ci --prefix frontend
make hooks
npm run test:e2e:install --prefix frontend
make verify
npm run test:ui --prefix frontend
```

`npm ci` на хосте нужен для проверок/разработки; Docker сам устанавливает
зависимости приложения во время сборки. Проверь `git config --get core.hooksPath`:
ожидается `.githooks`. Создание и активация GitHub-аккаунта, системные пароли
и разрешения выполняются пользователем в соответствующем UI, если потребуются.

## Настоящее приглашение и первый вход — сделай сам

На новом local-стенде identity-service создаёт bootstrap-администратора и
записывает путь в поле `invite_url` сообщения `bootstrap admin invite`.
Получи **реальный путь из логов его контейнера на этом Mac**:

```bash
docker compose --env-file .env -f deploy/docker-compose.yml logs --no-color identity-service
```

Сформируй ссылку `http://127.0.0.1:3200` + полученный `/invite/...`.
Используй один origin для открытия приложения и регистрации. Покажи эту
готовую кликабельную ссылку пользователю **в его личном чате с агентом** и
сам открой её в браузере. Можно указать login из той же записи логов.
Не выдавай пример `<token>` за рабочую ссылку, не генерируй токен вручную,
не используй приглашение с компьютера Артёма или с общего сервера.

Помоги пользователю завершить регистрацию. Пароль он задаёт в форме браузера;
не проси пересылать его в чат. Если приложение требует настройку 2FA, объясни
действия по одному; секрет и recovery-коды пользователь сохраняет у себя.
Убедись, что после регистрации открыт рабочий интерфейс. Не заявляй успешный
вход только по наличию приглашения. Обычный адрес после регистрации —
`http://127.0.0.1:3200`.

Приглашение одноразовое. Если используется существующая база и нового
`bootstrap admin invite` нет, помоги войти в имеющийся аккаунт; если нужен
новый invite, используй штатную выдачу действующим администратором. Не
сбрасывай БД/volumes, не меняй чужой пароль и не создавай скрытый обход входа.
Сырой токен можно показать только владельцу этого local-стенда в личном
чате по его запросу; не помещай его в Git, MD, общий отчёт или скриншоты.

## Удобный запуск без команд

Создай **на Mac пользователя**, рядом с его привычными файлами (по умолчанию
на рабочем столе), три локальных запускаемых `.command`-файла:

- `Запустить Order Fill.command` — запускает Docker Desktop, дожидается
  движка, проверяет существующий проект и разрешённую ветку, поднимает local
  Compose без удаления данных, дожидается готовности и открывает UI.
- `Открыть Order Fill.command` — открывает UI; если приложение не работает,
  понятно предлагает воспользоваться «Запустить Order Fill».
- `Остановить Order Fill.command` — останавливает только Compose этого
  проекта с сохранением volumes. Не завершает остальные Docker-проекты.

Сгенерируй их под фактический путь проекта и выдай executable-bit (`chmod +x`).
Корректно экранируй пути с пробелами, настрой PATH для Finder, обнаруженных
Docker CLI и Homebrew. Не вшивай путь другого разработчика или секреты.
Не перезаписывай одноимённые пользовательские файлы вслепую. Не добавляй
эти машинозависимые файлы в Git. Проверь запуск из Finder, а не только
из терминала с уже настроенным PATH. Если macOS блокирует открытие,
помоги пройти обычное системное подтверждение без отключения защиты.

Повторный запуск не выполняет `git pull`, переключение веток, миграции
вручную или автоматическое обновление зависимостей. Он использует текущую
разрешённую рабочую копию (`igorfrum` или `feat/igorfrum-*`); если выбрана
другая ветка, завершается с понятным сообщением. Обновление приложения
делает агент отдельно, после проверки Git и сохранения изменений.
Проверь, что кнопка остановки действительно сохраняет данные и последующий
запуск возвращает приложение. Подскажи пользователю, что закрытие вкладки
браузера не останавливает контейнеры, а выключенный Docker мешает запуску.

Проверь вход и навигацию в браузере. Для проверки обработки Excel используй
доступные разрешённые fixtures; отсутствие приватных файлов не считай
успешным тестом реальной обработки. Каталог `testdata/private/` не приходит
из Git и заполняется владельцем данных отдельно.

Для быстрой разработки UI при работающем backend можно остановить только
Compose frontend и запустить Vite, освободив порт 3200:

```bash
docker compose --env-file .env -f deploy/docker-compose.yml stop frontend
npm run dev --prefix frontend
```

Локальный Vite перенаправляет `/api` на `127.0.0.1:8080`.
`make down` останавливает стенд с сохранением volumes. Не применяй `down -v`
или `docker system prune --volumes` для исправления обычных ошибок запуска.

## Ветки и ежедневная работа

Твоя база — `igorfrum`. Временные задачи — только `feat/igorfrum-*` от неё.
Прямые коммиты в базовую `igorfrum` запрещены; результат передаётся через PR.
`dev`, `artemch`, `main` в этом профиле не используются и не изменяются.
Пользователь описывает задачу обычными словами, всю механику Git ведёшь ты.

Перед новой задачей на чистой рабочей папке:

```bash
git fetch origin --prune
git switch -c feat/igorfrum-<краткое-имя-задачи> origin/igorfrum
```

Если есть чужие изменения, сохрани их и используй отдельный worktree.
Вноси изменения в feature-ветке. Сначала найди owner и сформулируй ожидаемое
поведение, затем сделай правку и проверь её. Не смешивай задачу с массовым
рефакторингом, обновлением всех зависимостей или сменой дизайна.

Коммит — только после `make verify`. Push запускает его ещё раз через hook.
Для PR явно указывай целевую ветку: default branch репозитория — `main`,
поэтому не полагайся на значение по умолчанию в интерфейсе GitHub или `gh`.
PR направляй **только в `igorfrum`**. Перед каждым push проверяй текущую
ветку; допустима только `feat/igorfrum-*`. Задавай назначение явно:

```bash
git push -u origin HEAD:refs/heads/feat/igorfrum-<краткое-имя-задачи>
gh pr create --base igorfrum --head feat/igorfrum-<краткое-имя-задачи>
```

Не используй bare `git push`, `--all`, `--mirror`, wildcard refspecs,
force push или `--no-verify`. Не отправляй `HEAD:dev` и не запускай
перенос изменений в `dev`/`artemch`. Слияние PR в `igorfrum` выполняй
только по поручению пользователя после проверок; явно проверяй base PR.
Если `gh` недоступен, открой сравнение нужных веток в GitHub и помоги создать
PR с base `igorfrum`; не перекладывай выбор правильной базы на пользователя.

Правила защиты веток проверяй в GitHub: локальный hook не заменяет серверную
защиту. На момент передачи её включение требовало доступа владельца; этот
файл не является подтверждением, что защита уже включена.

## Проверки перед передачей изменения

```bash
make verify
```

Команда проверяет toolchain, документацию, OpenAPI, Buf, frontend lint/tests/
component/build, Go lint/SAST/tidy/build/tests и Compose. После изменения UI:

```bash
npm run test:ui --prefix frontend
```

Это unit + component + Playwright. Локально Chromium открывается на экране;
агенту нужен доступ среды к запуску браузера. Моки E2E не подтверждают работу
реального backend. Для live Excel-сценариев смотри `frontend/e2e/README.md`
и `testdata/README.md`; учётные данные и fixtures передаются отдельно.

При изменении зависимостей, auth, сети или обработки файлов дополнительно:

```bash
make security
npm audit --prefix frontend
```

Go-тест отдельного сервиса запускается из его модуля с `GOWORK=off`.
После изменения `.proto` выполни `make -C backend proto-gen`, обнови обе
стороны RPC и закоммить исходники вместе с сгенерированным Go-кодом.
Generated-файлы вручную не исправляй. При изменении HTTP API обновляй
OpenAPI, gateway-тесты и клиент вместе. Миграции добавляй новыми файлами.
Таблицы env/RPC/HTTP обновляй через `make docs-sync`; проверь diff.

CI добавляет Go race/shuffle и проверку уязвимостей. `Required checks`
агрегирует обязательные CI-этапы, но не включает Playwright и `npm audit`.
Не называй зелёный CI доказательством прохождения этих двух проверок.

## Общий сервер — не часть задания

Push в `igorfrum` запускает CI, но **не публикует** её на существующий сервер.
Автодеплой в текущем workflow выполняется только после push в `dev` и
успешных обязательных проверок. Не меняй deploy branch или self-hosted runner
для настройки личного компьютера друга.

Для этой рабочей копии допустим только локальный Docker Desktop. Если
пользователь просит «выложить», объясни: ты можешь подготовить PR в
`igorfrum`; решение о переносе на общий сервер принимает владелец проекта.
Не подключайся к общему серверу и не меняй runner. Для отдельного production
нужно отдельное согласованное задание владельца вне этого профиля.
Vercel-конфигурация публикует лишь frontend, а не весь стек.

`.env`, TLS private keys, пароли, токены, invite-ссылки и реальные workbook
не должны попадать в Git, этот файл или диагностический отчёт. Локальные
значения `.env.example` не подходят для production. Не копируй `.env`
другого разработчика или действующего сервера в новый стенд.

## Если что-то не работает

Сначала воспроизведи сбой и зафиксируй команду, exit code и короткий фрагмент
ошибки без секретов. Проверь, где проблема: окружение, сеть, конфигурация,
контракт или приложение. Меняй одну причину за раз.

- Docker недоступен: проверь daemon и права, не удаляй volumes.
- `npm ci` / Go download не проходят: проверь DNS/TLS/прокси и доступ к
  registry, затем повтори загрузку. Не отключай TLS-проверку сертификатов.
- Docker build падает на `mirror.gcr.io`: проверь сетевой доступ; единичный
  таймаут допускает повтор этапа. Повторяющийся сбой требует диагностики.
- E2E зависает на `page.goto` с ожиданием `load`: проверь сетевые запросы,
  включая внешние Google Fonts. Не увеличивай timeout и не удаляй assertions
  без подтверждения причины. Не запускай параллельно два набора с одним
  каталогом test-results.
- Порт 3200 занят: выясни, работает ли Compose frontend или другой Vite.
- `/readyz` зелёный: всё равно проверь downstream и пользовательский сценарий.
- Нужны права GitHub Admin: укажи это владельцу; Write достаточно для кода,
  но не для настройки защиты веток.

## Что должно быть в отчёте агента

Укажи ОС и версии инструментов, ветку/SHA, что установлено, какие контейнеры
работают, как разработчику открыть UI и войти. Отдельно перечисли команды
проверок с результатами, обнаруженные ограничения и следующие действия.
Различай «пройдено», «упало» и «не запускалось». Для изменений перечисли
затронутые файлы и статус commit/PR/push/deploy. Не заменяй проверку обещанием
«должно работать» и не выдумывай выполненные действия на чужом компьютере.

Основной ответ человеку сделай коротким: «Готово», ссылка на приложение,
названия трёх кнопок и результат первого входа. Одноразовую локальную
invite-ссылку покажи отдельно в его личном чате при первом входе; повторно
публиковать использованный токен не нужно. Технические подробности и
ограничения вынеси ниже. Не заставляй пользователя изучать этот файл,
чтобы просто открыть приложение или описать следующую идею.
