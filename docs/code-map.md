# Карта кода и проверка расчётов

## Архитектура

Приложение работает в браузере без серверной базы. `index.html` задаёт интерфейс, `src/app.js` управляет загрузками, редактированием и скачиванием, `src/workbookProcessor.js` содержит обработку Excel и бизнес-расчёты, `src/styles.css` задаёт оформление.

`.xlsx`/`.xlsm` читаются как ZIP-пакет XML через `loadXlsx`. `saveXlsx` сохраняет пакет и включает пересчёт формул Excel. Старые `.xls` конвертируются через SheetJS в `loadWorkbook`. Формулы и макросы современных бланков сохраняются в исходном пакете; вычисляемые платформой поля заменяются рассчитанными значениями.

## Общий путь данных

```mermaid
flowchart LR
  Upload[Файл из формы] --> Load[loadWorkbook / loadXlsx]
  Load --> Merge[mergeTyumenSources при двух таблицах]
  Merge --> Fill[fillWorkbook]
  Fill --> Source[readSource]
  Source --> CHZ[rebuildSourceWithChz]
  CHZ --> Calc[recalculateSourceTable]
  Calc --> Match[Сопоставление с бланком]
  Match --> UI[Редактируемый отчёт]
  UI --> Edits[applyFinalEdits]
  Edits --> Save[saveXlsx / скачивание]
```

Для обычного города `fillWorkbook` получает одну исходную таблицу без объединения. Для Тюмени предварительно объединяются исходные показатели двух таблиц. `readSource` повторно пересчитывает результат по тем же правилам; дополнительные колонки мест хранения не входят в расчёт продаж.

## Основные функции

| Функция | Ответственность |
| --- | --- |
| `detectColumns` | Поиск колонок источника/бланка по заголовкам |

| `newProductCalculation` | Обнаружение новинки и её целевой запас |
| `adjustQuantityForBrand` | Порог рекомендации и правила кратности бренда |
| `fillWorkbook` | Сопоставление таблицы с бланком, запись количеств, отчёт |
| `applyFinalEdits` | Ручные правки бланка и факта в исходной таблице |

## Новые функции двух складов

`mergeTyumenSources(options)` получает `officeWorkbook`, `warehouseWorkbook`, `brand`, имена обоих файлов. Возвращает новый workbook на основе шаблона склада. Входные workbook не изменяются. Включает объединение ЧЗ, проверку однозначности ключей/названий, совпадения периодов, суммирование первичных данных, очистку старых фактов и пересчёт. Дописывает расположение остатков и обновляет XML dimension, иначе сторонние Excel-читатели могут не увидеть новые колонки.

`tyumenRows` создаёт индекс позиций каждого источника. Уже объединённую таблицу нельзя подать в качестве одного из двух исходников, иначе остатки удвоятся. При отсутствии артикула применяется точный нормализованный ключ названия. Разные названия одного артикула в новой процедуре блокируются для проверки человеком.

`alignTyumenKeys` сопоставляет точные нормализованные названия между двумя таблицами, если хотя бы на одной стороне нет артикула. Известные разные артикулы по совпадению названия не объединяются. Несколько кандидатов или несколько строк офиса на одну строку склада блокируют объединение.

`warehouseTransferQuantity(officeStock, warehouseStock)` реализует чистую формулу распределения 25/75. `buildTyumenWarehousePlan(options)` возвращает строки `{ article, name, officeStock, warehouseStock, target, quantity }`. Отрицательные и дробные остатки для поштучного перемещения блокируются.

`northTyumenFreeStock(stock, inTransit, plannedOrder, target, warehouseStock, warehouseTransit)` ограничивает общий свободный запас доступностью через склад. Эта функция используется и первоначальным расчётом, и интерактивным пересчётом `recalculateNorthRow` в `app.js`. Если данные отдельных мест отсутствуют (`null`), сохраняется старый расчёт. Нулевой склад (`0`) принципиально отличается от отсутствующих данных.

`readNorthTyumenAvailability` читает отдельные колонки склада. Поля `tyumenWarehouseStock` и `tyumenWarehouseTransit` сохраняются в строках плана и передаются обратно через `recalculateEditedNorthPlan`, чтобы ограничение не пропало при скачивании после ручных правок.

Интерфейс склада использует существующий генератор `transferWorkbookBytes` с получателем «Склад Тюмень» (офис). Отправитель всех перемещений, включая Север, «СКЛАД ДОСТАВКА». Это точные названия 1С, подтверждённые пользователем. Фраза «СКЛАД ДОСТАВКА» распознаётся как Тюмень при проверке города исходного файла. Редактируемое количество проверяется на целочисленность, неотрицательность и складской лимит. Изменение файлов или бренда сбрасывает результат; счётчик ревизии не даёт завершившейся старой загрузке вернуть устаревшую таблицу.

## Проверка

```bash
npm run test:tyumen
npm run build
```

`scripts/test-tyumen.mjs` создаёт собственные небольшие workbook и проверяет объединённые продажи/выручку, смену категории, новую рекомендацию, сохранность входных данных, позиции только одного места, правило 25/75, конфликт артикулов, защиту от повторного объединения, ограничение склада для Севера и итоговые количества Excel. Файлы-примеры записываются в игнорируемый `test-output/tyumen`.

`scripts/check-tyumen-ui.mjs` проверяет интерфейс и выгрузку через Playwright. Запускать при работающем сервере на 3201; другой URL задаётся `TEST_URL`. Использует установленный `playwright` либо путь `PLAYWRIGHT_MODULE`. Для системного Chrome доступна переменная `CHROME_PATH`. Проверяет desktop/mobile, ручную правку, складской лимит, получателя и количество в выгрузке.

```bash
npm run dev -- --port 3201
node scripts/check-tyumen-ui.mjs
```

Старый `npm run test:workbook` зависит от личных файлов в Downloads и может остановиться с ENOENT, если их нет. Не считать его успешно пройденным при такой ошибке.

## Границы

Резервирование, проведение документов в 1С и хранение истории не реализованы. Скачанный заказ является документом-планом. Количества в пути не считаются физическим остатком в разделе «Склад Тюмень», но участвуют в плановом расчёте Севера. Прочие правила брендов остаются в существующих обработчиках. Изменения этой задачи выполняются в ветке `main`.

Бизнес-формулы, примеры и рабочий порядок: [Тюмень: методика](tyumen.md).
