# Auth, компании и история выгрузок

Дата: 2026-09-01  
Статус: согласовано. Реализация — `docs/plans/2026-09-01-auth-tenancy-implementation.md`.

## Зачем

Публичный HTTP API сейчас без аутентификации (`security: []` в OpenAPI). Джобы — UUID без владельца: кто знает `job_id`, читает отчёт и Excel. Нужны вход, изоляция между клиентскими фирмами и лента старых выгрузок, из которой можно снова поправить отчёт и скачать файлы.

`document-service` по-прежнему не знает пользователей. Права и сессии живут только в `api-service`. Браузер не парсит Excel.

## Кто есть кто

Три роли, без произвольного RBAC.

| Роль | Принадлежность | Видит |
|---|---|---|
| `platform_admin` | ни к какой компании | все компании, всех пользователей, все джобы и файлы |
| `company_admin` | одна компания | пользователей и все джобы своей фирмы; чужая компания — 404 |
| `purchaser` | одна компания | только свои джобы (`created_by` = он) |

Пользователь принадлежит **одной** компании, либо ни одной (`platform_admin`). Один человек в двух фирмах — не в этом релизе.

Платформенный админ — суперпользователь, не «метаданные без Excel». Каждое открытие чужой компании или джобы пишется в аудит (кто, когда, какая фирма/джоба), без содержимого файлов в логе.

## Что не делаем в v1

- SSO, JWT в `localStorage`, API-ключи, 2FA
- временный пароль, который задаёт админ
- саморегистрация и «забыл пароль» без админа
- роли кроме трёх выше
- биллинг
- удаление джобы клиентом и удаление компании с объектами в MinIO (только `disabled`)
- версии файлов после повторной финализации (новый Excel **перезаписывает** старый)
- SMTP: invite-ссылку копируют из UI и отправляют как угодно

## Онбординг и сессия

Саморегистрации нет. Пароль задаёт только сам пользователь по одноразовой invite-ссылке (TTL порядка 72 часов). Сброс доступа — новая ссылка: старый пароль и все сессии этой учётки сразу недействительны.

Повседневный вход: логин + пароль. Сессия — непрозрачный id в cookie `HttpOnly`, `SameSite=Lax`. Для HTTPS в проде — ещё `Secure` (выключается для локального HTTP).

Первый `platform_admin`: при пустой таблице пользователей процесс поднимает bootstrap (логин из env) и пишет одноразовую invite в лог. Пароль в `.env` не кладём.

Логин глобально уникален.

## Изоляция данных

- Таблица `companies`: имя, `created_at`, `disabled_at`. Выключенная компания: никто из неё не логинится, строки не удаляем.
- `users`: `company_id` (NULL у платформы), login, password_hash (argon2id или bcrypt), role, `disabled_at`.
- `sessions`: id, user_id, expires_at.
- `invite_tokens`: одноразовый секрет, user_id, expires_at.
- `jobs.company_id`, `jobs.created_by`. Старые джобы без автора видит только `platform_admin`.

Правило ответа: чужая фирма и чужая джоба для закупщика — **404**, не 403.

Создание джобы всегда пишет `company_id` и `created_by` текущего пользователя. Платформенный админ, если сам создаёт джобу, должен явно указать компанию (контекст выбранной фирмы в UI).

## HTTP

Все `/api/v1/*` требуют сессию, кроме:

- `GET /healthz` — открыт (Docker healthcheck)
- `POST /api/v1/auth/login`
- `POST /api/v1/auth/invite/{token}` — установка пароля по приглашению

`GET /metrics` снаружи без сессии не отдаём (внутренняя сеть или тот же auth).

Новые поверхности (имена ориентир, контракт правится в `packages/contracts/openapi.yaml`):

- `POST /api/v1/auth/login` / `logout`, `GET /api/v1/auth/me`
- `GET /api/v1/jobs` — лента: purchaser свои; company_admin — фирма; platform_admin — все, фильтр по `company_id`
- компании: список/создание/выключение — только платформа
- пользователи внутри фирмы: company_admin своей, платформа любых; создание = новая invite-ссылка
- сброс доступа = новая invite, инвалидация сессий

Существующие `GET/POST .../jobs/{id}/...` получают проверку `company_id` + `created_by` по роли. Повторные правки завершённой джобы **уже разрешены** доменом (`CanAcceptEdits` для `needs_review` и `completed`): лента открывает ту же карточку, отчёт правится, финализация перезаписывает outputs.

Failed джоба в ленте видна; заново залить исходники — **новая** джоба.

## Frontend

Тонкий UI, без бизнес-правил Excel.

Экраны: логин; invite (два поля пароля); лента выгрузок; текущий мастер джобы; админ компании — пользователи; платформа — компании и при необходимости любая лента.

Без сессии мастер загрузки недоступен. Протухшая сессия — экран входа, возврат на тот же URL джобы, если она всё ещё своя.

## Same-origin и cookie

Сейчас UI `:3200`, API `:8080` — разные origin. Для cookie:

- nginx фронта проксирует `/api/` на api-service;
- Vite `server.proxy` на тот же префикс в dev;
- `credentials: 'include'` на `fetch`;
- CORS в проде — конкретный origin или вовсе не нужен за одним origin.

`document-service` порт 8081 на хост не публикуем как API.

## Безопасность (норматив v1)

Это не «потом ужесточим», а обязательная часть релиза. Права на сервере; UI только прячет кнопки.

**Секреты и криптография**
- Пароль: argon2id (`golang.org/x/crypto/argon2`), уникальная соль из `crypto/rand`. Не MD5/SHA и не обратимое шифрование.
- Сессия и invite: 32 байта из `crypto/rand`, в cookie/URL — сырой токен, в Postgres — SHA-256. Сравнение `crypto/subtle`.
- Логин: один и тот же 401 для «нет пользователя», «плохой пароль», «выключен». Если пользователя нет — всё равно гоняем Verify против dummy-хеша, чтобы не светить таймингом.
- Пароль: минимум 10 символов, максимум 1024 (защита от огромного тела). В логах паролей, cookie и сырых токенов нет.
- Bootstrap: в лог один раз invite-URL, не пароль. `BOOTSTRAP_ADMIN_LOGIN` — не секрет.

**Сессия и CSRF**
- Cookie `order_fill_session`: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` только если `SESSION_COOKIE_SECURE=true` (прод с HTTPS).
- Не класть токен в `localStorage` / `sessionStorage`.
- Мутации (POST): заголовок `X-Requested-With: fetch` и Origin из allowlist (или пустой Origin у same-origin non-CORS). Same-origin через nginx/Vite proxy — основной анти-CSRF; заголовок — второй слой.
- Logout и сброс invite убивают все сессии этой учётки.

**Авторизация**
- Каждый `.../jobs/{id}/*` проверяет роль. Чужое — 404. Не полагаться на «id не угадают».
- Создание джобы без `company_id` у `company_admin`/`purchaser` невозможно; платформа передаёт выбранную компанию явно.
- `/metrics` — только `platform_admin`. `/healthz` открыт.

**Злоупотребления и периметр**
- Rate limit: логин (по IP+login) и `POST` создания джобы (по user id). In-memory ок при одной реплике api-service.
- Тело запроса: уже есть лимит загрузки; JSON auth — `http.MaxBytesReader` (порядка 8 KiB).
- `http.Server`: кроме `ReadHeaderTimeout` задать `ReadTimeout`, `WriteTimeout`, `IdleTimeout`, `MaxHeaderBytes`.
- CORS: не `*` вместе с cookie. После same-origin proxy в docker CORS можно держать узким allowlist для dev на разных портах. `Access-Control-Allow-Credentials: true` только с конкретным Origin.
- Security headers на API и на nginx фронта: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` (или CSP `frame-ancestors 'none'`), `Referrer-Policy: no-referrer`.
- Docker: Postgres/Redis/MinIO слушают `127.0.0.1`, не `0.0.0.0`. TLS — на reverse proxy, не в Go.
- SQL только плейсхолдерами. Аудит без тел Excel и без секретов.

## Сопутствующее (инфра)

- `VITE_*` не содержит секретов; после proxy база API — пустая (относительные `/api/...`).
- В проде `API_ALLOWED_ORIGINS` не `*`.

## Тесты (минимум)

- Закупщик A не читает джобу закупщика B (404), даже зная id.
- Админ компании видит обе джобы своей фирмы, не видит другую фирму.
- Платформа видит всё.
- Выключенный пользователь и выключенная компания не логинятся.
- Invite одноразовая и протухает.
- Сброс убивает старые сессии.
- `/healthz` без cookie — 200.
- `CanAcceptEdits` на completed по-прежнему проходит под владельцем / админом фирмы.
- OpenAPI: схема security для защищённых путей.

## Граница сервисов

```
браузер → frontend (nginx / Vite proxy) → api-service → postgres
                                         → redis → document-service
                                         → minio
```

Воркер обрабатывает джобу по id из очереди, как сейчас. Новых полей в Excel-правилах нет.
